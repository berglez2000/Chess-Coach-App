# ChessLink recorder

This is an experimental direct Web Bluetooth recorder, not a verified M830 hardware driver. No physical board was available during implementation. Synthetic protocol fixtures and simulated browser GATT devices validate the software path. The user subsequently provided an actual firmware 1.64 trace for d4/e6/e4/d5, now used to verify decoding and slow pressure-square transitions; physical acceptance for the complete feature remains pending.

The implementation independently follows the [Magic Chessboard protocol description](https://github.com/domschl/python-mchess/blob/main/mchess/magic-board.md). The public [bluepy transport](https://github.com/domschl/python-mchess/blob/main/mchess/chess_link_bluepy.py) identifies the notification/write characteristics and parity encoding. The service and characteristic identifiers match [Microchip's transparent UART service](https://onlinedocs.microchip.com/oxy/GUID-26457D23-798C-47B0-9F40-C5DA6E995C6F-en-US-2/GUID-A7263185-4F92-4567-9A18-7433617D925E.html). No third-party implementation code is bundled.

By default, listen-only mode sends no ChessLink commands. With listen-only disabled for troubleshooting, only `V` and `S` queries are written, with ASCII XOR block checksums and odd parity. Notifications are decoded across arbitrary BLE packet boundaries, validated by checksum, and mapped from A8–H1 piece codes to FEN placement. No reset, LED, EEPROM, mode switch, or automatic-report configuration commands are sent. One version query and one initial position query are sent per connection, with 15-second operation deadlines. After that, recording listens only to unsolicited notifications, to avoid repeated queries potentially interfering with the King’s LED prompts. The user confirmed that King LED prompts work in listen-only mode; initial-query mode did not preserve them on their board. The bounded diagnostic download contains incoming hex bytes and generic connection/decode events; it does not include Bluetooth addresses, account identifiers, or player names.

Position matching uses the complete piece placement against legal chess.js successors. It deliberately does not use received placement to invent castling rights, turn, or missed moves. Older positions require a confirmed takeback. Unknown piece codes, occupancy-only data, or alternative move-event protocols do not produce moves; obtain real-board fixtures before implementing a different decoder. Real M830/ChessLink 1.64 frames for d4/e6/e4/d5 are now checked in under `tests/fixtures/chesslink/`. Separate departure presses are recognized as a legal move in progress, keeping recording active while waiting for destination/remaining-piece presses. If the M830 reports promotions as pawns until confirmed on its display, the session pauses and manual coordinate entry supports choosing `q`, `r`, `b`, or `n`.

Automatic recording is the default; confirmation mode remains available for troubleshooting. Automatic mode waits 800 ms after a changed position; a legal intermediate position can still be accepted if the user moves pieces slowly (especially rook-first castling). Move the king first when castling; use confirmation mode during troubleshooting and correction controls to reconcile history. Incoming square order is independent of the on-screen viewing side or the physical orientation reported by the user. Before recording, compare both forward and reversed status data with the complete known position, and lock the matching order for that connection. The stored `rotated` draft flag is retained for compatibility but now controls reversed incoming square order, with a correctly labeled manual override.

Account-scoped localStorage preserves each accepted move. These are local browser drafts, not server backups; another browser/device cannot recover them. Corrupt drafts are kept for recovery download until explicit discard. Tab hiding, mismatches, and disconnection pause recording. Quiet thinking time does not expire the last position: notification-only connections have no heartbeat, so a silent reporting failure cannot be detected until another report or disconnect. Resuming requires the currently reported placement to equal the recorded placement. Identical placements do not prove identical history; reconstruct any known missed moves explicitly.

The first save fixes the PGN snapshot. `recordingId` is a UUID accepted by the existing import endpoint; the server derives an owner-scoped SHA-256 game primary key. Repeated/concurrent requests return the same game only if PGN and user color agree. Other owners derive different keys. Regular PGN imports retain their original behavior. This needs no database migration.

## Real-board acceptance gate

1. Record the M830/ChessLink model and firmware versions, OS, browser version, and cable arrangement. Close other board clients and use a secure origin in desktop Chrome.
2. Set up the normal initial position with the built-in King enabled. Connect through **My games → Record board game**. Wait for **Synchronized**; download diagnostics if status queries do not yield positions.
3. Start recording in confirmation mode. Play a short game against the built-in King, physically execute each reply, and confirm each detected legal move. Verify the King continues choosing replies without switching to an external engine.
4. Check both colors, both incoming square orders, castling, captures, en passant, all promotions, takebacks, pause/reconnect, and reload. Test a disconnect with missed moves and confirm that history is not guessed.
5. Finish, confirm result, export PGN, save, and review it from My Games. Compare every move against the King's game record.
6. If status reports are absent during normal engine play, run a separate CLink-mode probe to establish whether the transport works only in that mode. The [M830 manual](https://computerchess.com/media/71/6d/c8/1648808903/M830_expert-manual_ENG.pdf) documents CLink separately. A successful CLink-only probe does not meet the built-in-King recording goal. Record the restriction and investigate a separate export workflow.

Retrieving the nine saved slots, USB/Web Serial, custom initial FEN, external engine play, and server-synchronized recording drafts are not implemented.

User-supplied SAN recovery rebuilds a complete normal-start sequence only when it preserves the existing recorded prefix and reaches a fresh reported placement. It does not infer missing moves or auto-start recording. Press Start/Resume in the connection panel and choose automatic acceptance or confirm each move.

LED troubleshooting: the default **Listen only (preserve King LED prompts)** mode subscribes to notifications without discovering the write characteristic or sending even initial V/S queries. It does not configure automatic reports. No initial report is guaranteed; a square press may trigger one. Compare prompts before connection, after connection, and after disconnect/restart. Loss of LEDs despite zero ChessLink commands suggests connection/firmware behavior, but needs hardware verification.

Follow-up hardware feedback: listen-only preserved LEDs but moves did not sync. Simultaneous LEDs and recording remain unverified. While paused, the troubleshooting panel allows separate explicit one-shot V/S probes, logged in diagnostics, to distinguish initialization effects. Listen-only does not guarantee positions; it sends no commands unless a query button is explicitly pressed.
